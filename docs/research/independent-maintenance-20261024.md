# 独立维护 Peri Cloud：功能盘点与上游评估

评估日期：2026-10-24。上游固定为 `KonghaYao/peri@e598d17872bce487355e1bfa70f077743984760f`；本发行完成本次合并后的源码为评估对象。本文是源码与本地模拟验证结论，不是线上质量证明，也不是要求本轮全部实现的路线图。

## 判断

可以从这个版本开始以自己的产品目标维护。上游值得保留为参考和补丁来源，但没有必要把它的每次重构变成我们的升级任务。

上游是一套功能丰富的本地 Coding Agent 产品，主线是终端、项目、代码工具、ACP 客户端、插件与多 Agent 编程。我们已经发展为账号中心的个人云助手：长期对话、主动联系、多设备执行、持久任务和隐私记忆。这两种产品共享模型循环与能力协议，但状态权威、运行位置和恢复要求不同。

不能用一个百分比衡量完成度。对本地编程工具，上游已有完整的使用链路；对我们的个人云助手目标，上游并非完整替代品。本发行的主要短板开始从“有没有基础设施”转为“能力能否统一使用、长程行为是否可靠、运维是否容易”。

## 1. 先理解上游各层在做什么

| 层 | 上游职责 | 本发行如何使用 |
| --- | --- | --- |
| `peri-model` | Anthropic / OpenAI-compatible 请求、流、用量与协议适配 | 复用，具体供应商仍需真实验证 |
| `peri-agent` | Session、消息队列、Receive → Compact → Reason → Act、工具调用与消息持久化接口 | 复用原循环，云端注入自己的存储与能力 |
| `peri-middlewares` | 权限、MCP、Skill、Goal、SubAgent、Hook 等切面与装配 | 选择性装配，未把所有本机能力向云用户开放 |
| `peri-resources` | 本机 SQLite / 远端存储、会话历史、资源定位 | 部分复用；CloudJournal 保持云端状态权威 |
| `peri-runtime` / `peri-controller` | 进程内多 Session 句柄、控制与事件转发 | 不作为云端持久任务调度器引入 |
| `peri-acp` | 协议请求、宿主装配、客户端交互与事件映射 | 当前只取提示词；Cloud 尚无兼容的 ACP 服务面 |
| `peri-tui` / `peri-theme` | 终端 UI、CLI / print、会话/模型/MCP/插件面板 | 本轮评估后不引入，原因见第 6 节 |
| builtin MCP 包 | Workspace 文件与 Shell、搜索、定时、工作流、产物等 | 依赖闭包保留；实际云端暴露以宿主装配为准 |

上游的子 Agent 可用定义启动，也可 fork 父历史；可后台运行、继续会话及追加要求。它的 `TaskManager` / mailbox / resource owner 管理当前进程的执行和消费责任。**持久保存会话不等于重启后恢复正在执行的任务。** 上游设计明确剥离 owner 冷恢复，不承诺重启后重建未保存的在途执行。

本发行的执行者由云端 `WorkerService` 派发，任务、执行会话、运行轮次和窗口分别持久记录。原调用结算和副作用恢复属于 Cloud / Executor 账本，不能用上游进程内 TaskManager 替换。

源码依据：[上游整体架构](https://github.com/KonghaYao/peri/blob/e598d17872bce487355e1bfa70f077743984760f/docs/design/architecture.md)、[异步任务边界](https://github.com/KonghaYao/peri/blob/e598d17872bce487355e1bfa70f077743984760f/docs/design/session-async-tasks.md)、[本发行架构](../architecture.md)。

## 2. 已实现与仍缺什么

以下“已实现”指存在接线后的运行路径；验证范围以[本轮同步记录](../upstream/peri-e598d178.md)及原专项验收为准。SDK 内有某模块，不等于 Cloud 已向用户交付该功能。

### Skill 与 MCP

| 能力 | 当前已实现 | 缺口 / 边界 |
| --- | --- | --- |
| 项目与全局 Skill | 认证执行器提供项目目录；账号 / 管理员明确安装全局目录；宿主计算遮蔽；按需加载正文 | 没有完整安装、更新、卸载与版本锁 UI；全局 Skill 辅助脚本不能自动传到设备执行 |
| 项目规则与助手人格 | `AGENTS.md` 优先，缺席回退 `CLAUDE.md`；独立助手级 SOUL；来源、摘要及裁剪有记录 | 不遍历任意父目录，不自动展开 `@import`；项目资料不是用户授权 |
| MCP 工具与资源 | 账号级公共 HTTPS 服务、连接版本刷新、状态帧、ToolSearch、原 PermissionMiddleware | Cloud 禁止 stdio / builtin / 宿主插件自动继承；不支持用户随意填写内网 endpoint |
| MCP Skill / Agent | 上游有发现、digest/frontmatter 校验、远端 Agent 加载实现 | Cloud 当前 `McpMiddleware` 未传入完整 Skill/command registry；执行者明确不装配外部 MCP。不能宣称远端 Skill/Agent 已可无缝委派 |
| 插件 / Hook / Workflow | 上游 SDK 与 builtin 包包含相应实现 | Cloud 装配明确关闭依赖本机 cwd、宿主进程或本机配置的路径；没有云账号隔离的通用插件部署机制 |

优先补一份统一的 Capability Catalog：来源、版本、可见范围、可执行位置、状态和加载入口统一表达；保留“目录便宜、正文按需”的装配。安装和更新应产生明确版本，不能让未观察到的技能更新静默改变任务。下一步再设计辅助文件到设备的受控投送。

项目 `.mcp.json`、私网 MCP、执行者使用外部 MCP 都涉及准入和身份扩展，应作为明确的产品决策；不能通过复制上游设置读取器顺便打开。

源码依据：[`CloudChainAssembler`](../../peri-cloud/src/assembly.rs)、[`CloudAgent`](../../peri-cloud/src/core.rs)、[账号 MCP 接线](../../peri-cloud/src/mcp/runtime.rs)、[Skill 目录与加载](../../peri-cloud/src/workspace/skills.rs)、[完整装配契约](../context-assembly.md)。

### 多设备管理

| 能力 | 当前已实现 | 缺口 / 边界 |
| --- | --- | --- |
| 身份与授权 | OAuth 人工同意、设备归属、撤销、原生凭据、设备连接租约 | 设备登记 / 租约记录均不代替实际认证与可用性检查 |
| 主助手直接执行 | 发现授权设备，prepare 冻结 target，再 execute；不切换全局默认设备 | target 是有期限的调用准备结果，不能无限沿用；没有自动“最佳设备”选择器 |
| 工作区与环境 | 规范路径与目录身份绑定，AGENTS / Skill / 固定应用环境快照 | 同路径替换需重新绑定；没有完整软件版本 / 运行健康探测和设备配置管理 |
| 并发与恢复 | 主助手和执行者共用操作账本及整设备写入占用；未知结果先查原调用 | 写入互斥保守，尚无可证明安全的子目录级并发；设备离线不自动迁移副作用 |
| 用户操作面 | 网页 / QQ 的设备和工作区选择、任务状态与操作查看 | 缺少统一设备健康页、排队原因、能力差异和工作区书签的完整体验 |

优先做“为什么这台设备不可用 / 为什么在排队”的可解释界面，再做选机策略。自动故障转移只能迁移尚未提交的意图，已提交或未知操作保持原设备身份并核实，不能换台机器再跑一次。

源码依据：[按调用设备契约](../device-invocations.md)、[任务恢复](../../peri-cloud/src/tasks/recovery.rs)、[执行器工作区](../../peri-executor/src/workspace.rs)。

### 个人 Agent 的心智模型

“心智模型”在这里指助手对身份、用户、当前意图、任务、设备和证据的组织方式，不指隐藏思考或人格自我声明。

| 层次 | 当前已实现 | 仍缺什么 |
| --- | --- | --- |
| 我是谁、如何与你说话 | 助手 SOUL、账号偏好、角色提示词与渠道表现适配 | 需要用户自己的稳定人格正文和行为验收样本；代码不能决定什么语气令人舒服 |
| 我对你知道什么 | USER / FLEET / DEVICE_ENV 条目、CAS、来源、有效期、遗忘、中文检索、隐私帧 | CONTEXT 项目记忆、候选箱、后台整理、长期关系与事实冲突处理未交付 |
| 你正在让我做什么 | 独立目标和任务、最新指令水位、主助手动态帧、插话和双向交流 | 仍需真实长对话检验“说完派活后是否自然聊天、何时报告、何时静默” |
| 我做到了哪一步 | 持久状态、trace / 会话详情、有界证据、产物和验收 | Bash 成功和产物覆盖只是证据条件；“做得好不好、是不是用户真正要的”仍需要主助手判断和真实验收 |
| 我何时主动联系你 | 持久计划、联系窗口、后台额度、静默策略、生成与送达分离 | 当前需要用户安排或授权；没有自由自主的全天情境感知或未经安排的自动关怀循环 |

建议增加一份有来源的“当前意图视图”：持续目标、活跃任务、待回复问题、明确偏好与最近承诺分别保存或投影，并在过期、取消、完成时退出。长期事实进入记忆，执行证据进入任务历史，短期聊天态度留在对话；不要把整段执行 trace 自动变成个人记忆。

这属于后续设计，不是本轮增加一套“人格数据库”。可先用已有 goal/task/memory 生成统一视图，评估真正缺失的字段后再扩展存储。

源码依据：[记忆边界](../memory.md)、[调度与主动消息](../scheduler.md)、[任务通信和历史](../execution-continuity.md)、[产物验收](../task-deliverables.md)。

## 3. 硬切窗口：现在的算法及 OpenAI 可借鉴之处

### 现有路径

主助手继续摘要式 Full，并用 Micro 投影收起可恢复的旧工具交换；执行者关闭摘要压缩，由任务宿主管理硬窗口。

执行者目前用可见历史的字节估算加系统 / 工具开销，与 `min(worker_window_tokens, model_context_window) - reserve` 比较。默认窗口 48000、预留 8000；这不是供应商精确 token 计数。宿主在模型 / 工具结算边界持久标记 rotate，再核实原操作、生成新窗口。新窗口注入完整活跃约束、宿主事实和有界笔记、旧操作引用及选定证据预览；历史按分页和版本检索，旧工具继续原归属结算。

已解决的重点是换窗不改变任务身份、权限或原操作，旧窗口不能摘要也能从账本接班。未解决的是最优切换时机和语义连续性质量。

当前缺口：

1. 字节估算粗，缺少按 provider 校准和请求级预算误差观测。
2. 缺少多阶段低预算提醒，执行者没有独立 `new_context` 类主动换窗工具；目前主助手可以 control_task rotate，worker 主要由宿主阈值换窗。
3. 交接笔记依赖运行期间已有更新，缺少专门的有界整理阶段；应预留整理额度，但失败时仍走宿主事实兜底。
4. 有窗口 / 原文分页与筛选，尚无统一的跨窗口语义索引、证据收藏与召回质量指标。
5. 没有真实模型的低窗口长程评测，也没有缓存率 / 延迟 / 成本实测。不能将模拟回归等同于模型不会遗忘约束。

源码依据：[窗口阈值](../../peri-cloud/src/tasks/suspension.rs)、[模型边界与事实帧](../../peri-cloud/src/tasks/middleware.rs)、[持久交接](../../peri-cloud/src/tasks/recovery.rs)、[原专项验收](../execution-continuity-verification.md)。

### OpenAI 的两条路径要分开

官方 Responses API 提供服务端阈值压缩，以及独立 `/responses/compact`。两者返回不透明的加密压缩状态；独立端点返回的完整窗口应原样用于后续请求。这是 provider 压缩能力，不等于清空历史后检索续接，也不能假设任意 OpenAI-compatible 服务实现了它。[官方 Compaction 文档](https://developers.openai.com/api/docs/guides/compaction)

另行核查了 OpenAI Codex 公开源码快照 `970111f6cb62cc02fe36a82ea7d71b37a2889c97`：

- `new_context` 是无参数工具，仅提出换窗请求，不重置环境状态。
- token-budget 换窗跳过模型 / 服务端摘要，仍经过 compaction 生命周期和 hooks。
- 宿主推进窗口 ID，重建当前 world-state / initial context，有条件地保留客户端指定内容，并重算用量；不是简单把整个消息数组清空。
- 模型目录的预算指引搭配 notes / history 引用；执行责任仍需外部状态支持。
- token 预算区分整个活跃上下文与扣除固定前缀后的增长，同时保留模型完整窗口硬上限。
- 实验激活有模型、后端、认证及套餐门槛。公开客户端有相关代码，不证明这些私有后端扩展能被我们的普通 API endpoint 调用。

公开源码依据：[工具](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/core/src/tools/handlers/new_context_window.rs)、[换窗生命周期](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/core/src/compact_token_budget.rs)、[初始状态重建](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/core/src/session/mod.rs#L4946)、[预算计算](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/core/src/session/context_window.rs)、[实验入口](https://github.com/openai/codex/blob/970111f6cb62cc02fe36a82ea7d71b37a2889c97/codex-rs/core/src/session/token_budget.rs)。官方配置也记载了 `total / body_after_prefix` 范围：[配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)。

建议适配其思路，继续由我们自己的持久任务层实现：

```text
观察请求预算 → 低预算提醒 → 保存工作笔记 / 证据引用
                     ↓ 自愿 rotate 或达到宿主硬阈值
封存旧窗口 → 核验原操作与最新指令 → 编译新窗口权威快照
                     ↓
恢复当前事实 + 必要引用 → 按需查询旧证据 → 继续同一任务
```

预算可以区分稳定前缀与任务增长，但最终请求必须受总窗口约束。先用能力适配器接入精确用量 / tokenizer，缺席时保守估算。旧窗口无法整理时直接使用宿主事实；不要求模型先完成数轮同步工具才能恢复权限。API 原生压缩可作为可选 provider 策略，不能替代任务账本或隐私校验。

缓存方面，换窗会改变活跃上下文前缀，可能损失已积累的前缀命中；重建稳定 system / 工具部分仍有复用机会。Micro 也会修改旧消息投影。实际权衡应看命中 token、总输入、检索回填、延迟和完成质量，而不是只追求缓存百分比。本轮没有测这些指标。

## 4. 上游完成度与维护风险

| 维度 | 评估 | 证据边界 |
| --- | --- | --- |
| 本地编程主流程 | 功能完整度较高 | README 有安装、模型配置、终端 / headless / ACP、恢复、工具、Skill、插件和编程协作；本轮没有安装运行完整上游 TUI |
| 核心工程质量 | 有较强的契约和回归基础 | 架构分层、类型化协议、权限链、归档与消费保护有实际实现，本发行针对闭包运行了大量测试 |
| 生命周期稳定性 | 仍在快速调整 | 明确取消了冷恢复保证，近期继续修改异步收尾、owner、事件与内存；不是接口已长期冻结的 SDK |
| 长期个人云助手 | 与目标有明显距离 | 本地项目定位；不自带我们的 OAuth 多用户、个人渠道、多设备执行账本和持久调度语义 |
| 全产品生产成熟度 | 本轮证据不足以断言 | 未验证完整上游 TUI、所有真实 MCP wire、所有供应商和长时间运行；仓库自身也记录未覆盖项 |

不能把 issue 文档里的“待修复 / 待 PR”当作当前代码仍坏的证明，文档可能落后。它们可说明维护范围和风险：上游内存专项明确保留了终态正文淘汰等未实现项，异步任务设计明确不提供冷恢复；本轮实际遇到的两个 Skill 夹具失败在其专项记录中已有基线复现说明。我们更新了测试夹具的已连接句柄，没有放宽生产校验。

参考：[内存驻留专项及明确延后项](https://github.com/KonghaYao/peri/blob/e598d17872bce487355e1bfa70f077743984760f/spec/issues/2026-10-23-p1-subagent-memory-retention.md)。测试数量不能替代产品行为验证，也不用于给作者打分。

## 5. 如何停止被上游更新牵着走

建议保留来源，冻结基线，独立演进；不为了“彻底自主”而重写已有可用内核。

| 归属 | 模块 / 数据 | 维护方式 |
| --- | --- | --- |
| 我们的产品权威 | Cloud、Executor、RemoteTools、ToolRuntime、Scheduler、账号 / 任务 / 记忆 / 渠道及其 schema | 由自己的需求和验收决定；上游不覆盖 |
| 冻结的借用内核 | Model、Agent、Middleware、Resources 与 builtin 能力闭包 | 固定来源版本；必要改动在补丁清单声明，逐项维护 |
| 可选参考 | 上游 ACP / TUI / CLI、工作流和产品提示词 | 按独立设计任务评估，不自动扩大依赖闭包 |

今后只在四类情况调查上游：影响已用路径的缺陷或安全修复；供应商协议变化；确实需要的新能力；有实测收益的性能优化。普通重命名、提示词调整、框架重构无需跟进。不设每日全量同步要求，也不创建自动合并任务。

每次引入先写“我们的哪个问题 → 哪个调用路径 → 保持哪些契约 → 用什么验收”。更新前保留原 manifest 和许可证，分组移植或有界三方合并；依赖升级不与产品语义改变捆绑。`check-upstream.py` 继续检查未声明漂移，清单是来源证据，不是上游必须决定我们接口的约束。

建议后续逐步把 deployment archive、任务快照、能力目录这些接缝保持为窄端口；内部无需为了 upstream diff 更小而保留重复状态机。改内核时把原因和关键回归留在本仓库，之后可以明确拒绝不适合的上游变更。

## 6. TUI 值不值得拿

终端入口对本地工作有价值，用户对 TUI 的用途变化是合理的。但本次不把完整上游 TUI 并入云端发行，评估结果是适配量偏大，符合“难度大就算了”的边界。

实际盘点（含测试，不是新增产品代码量估算）：`peri-tui` 518 个 Rust 文件 / 162613 行，`peri-acp` 298 个 / 97999 行；还需 Controller、Runtime、Theme、Langfuse 和 UI 依赖。TUI 启动器会打开自己的 Resources、建立本地 ACP server/client、读取模型和插件设置，不是一个仅消费本发行 HTTP API 的可替换皮肤。

直接编译它可以得到另一个本地 Coding Agent，但不会自动得到我们的账号、主会话、任务、审批和设备。若两边各自维护状态，会造成两个“主控”，并增加后续追上游的负担。

| 方案 | 价值 | 成本与建议 |
| --- | --- | --- |
| 独立使用固定版本上游二进制 | 立即获得本地终端编程工具 | 与云端个人助手分开；不冒充共享任务，不为它改生产宿主；本轮不安装 |
| 把上游 TUI 整包纳入当前工作区 | 终端体验丰富 | 增加大批依赖与第二套宿主，当前不选 |
| 以后做 Cloud 终端客户端 | 和 QQ / Web 操作同一会话与账本 | 需要云端事件 / 审批 / 恢复协议适配，可借鉴组件，按独立项目评估 |

如果真正要的是在终端和同一个云端助手聊天，优先考虑第三种：先定义现有 HTTP / 事件能力的客户端契约，再判断复用上游渲染器是否比写一个小客户端更省维护。那时应显式修订 AGENTS 的 TUI 边界并确保服务端构建不依赖 UI；本轮没有偷换这条工程约束。

源码依据：[TUI 依赖](https://github.com/KonghaYao/peri/blob/e598d17872bce487355e1bfa70f077743984760f/peri-tui/Cargo.toml)、[启动装配](https://github.com/KonghaYao/peri/blob/e598d17872bce487355e1bfa70f077743984760f/peri-tui/src/launch.rs)、[上游使用方式](https://github.com/KonghaYao/peri/blob/e598d17872bce487355e1bfa70f077743984760f/README.md)。

## 7. 我会怎样安排下一轮

| 优先级 | 工作 | 可验收结果 |
| --- | --- | --- |
| 先收敛当前版本 | 模拟回归、来源校验、schema 25 迁移与回滚说明，明确真实调用 / 生产升级边界 | 同步记录与 Git 提交可复查，未验证项不包装成上线完成 |
| 下一轮第一项 | 统一能力目录、Skill 版本与辅助文件的设备投送设计 | 能解释一个能力来自哪里、在哪执行、为什么可见；不扩大账号权限 |
| 下一轮第二项 | worker 预算提醒、主动换窗、交接笔记和证据引用 | 低预算下保持任务连续；不改变原操作身份；分别观测成本与质量 |
| 下一轮第三项 | 个人助手当前意图视图与设备健康解释 | 主助手能自然回答“你在忙什么 / 还等什么 / 能在哪台设备做” |
| 需要另外授权的验收 | 真实模型、真实渠道和生产升级 | 长程行为、缓存与费用、实际主动投送、生产备份恢复都有直接证据 |

这些是维护建议，未自动创建计划或承诺周期任务。建议先把当前版本稳定使用一段时间，再决定哪个缺口最影响日常，而非继续按上游更新顺序施工。
