## 1. Micro Compact：最契合我们的上下文问题

它不是调用模型总结历史，而是保存原始记录，再生成更小的模型视图。旧的大段 Read、搜索和工具回执可以从活跃上下文中收起，通过引用按需查询原文。它减轻上下文占用，但不能消除所有语义污染，也没有证明本项目实际缓存命中率或延迟会改善多少。

上游为收起历史设置了几个重要条件：工具交换已闭合，没有待完成义务；结果已进入成功的模型请求并持久化；原文可恢复且存在授权读取能力；调用、回执及协议依赖保持完整。用户要求、未决操作和仍需处理的异步结果受到保护。

归档先完成原文写入和可恢复性校验，再提交投影与目录，最后发布内存视图。完整摘要压缩也要保留必要的归档引用及未处理结果。这些措施比仅在提示词里要求“重要信息不要丢”可靠。

但不能直接启用：本项目通过 CloudJournal 管理历史及结算，在 `peri-cloud/src/core.rs` 创建的 Session 没有传入上游归档资源。本次检查也未发现 Cloud 现成的 ContextArchive/ArchiveRead 适配。任务 trace 查询并不等同于完整对话原文归档。

实施前需补齐：

1. CloudJournal 的原文、投影、目录和版本一致性接口。
2. 绑定真实用户、会话和隐私范围的归档读取能力。
3. 重启恢复、归档不可用时的保守行为，以及主会话压缩和执行者硬换窗的协作。
4. 有界读取和真实请求装配验证；不能全量回填历史抵消压缩收益。

主 agent 的摘要式压缩和执行 agent 的硬换窗仍保留，Micro Compact 可以作为它们之前的减负步骤。

## 2. 异步结果：已送达不等于主 agent 已处理

上游增加独立的 DeliveryReceipt 与 ProcessingReceipt：结果进入消息记录后，仍可能尚未被模型实际处理。这类结果在处理前不能被普通摘要或模型视图投影吞掉。对于我们的“主 agent 继续聊天、后台任务异步完成”，这个区分值得审查并吸收。

另一个修复让交接事件的身份与确定的载荷相符：旧版身份只依赖 pending task 集合，载荷却包含每次不同的等待时长，可能产生同一 ID、不同内容。新版规范化任务顺序，等待时长仅记日志，身份包含载荷版本及规范内容。

这些属于上游 Session/MCP 路径的变化，不能直接推断 Cloud 自有任务路径已经存在同样故障，也不能假定升级后 Cloud 事件就自动获得消费保护。需要逐个检查桥接点。

尤其注意，上游最新异步任务设计仍以当前进程内的任务目录、mailbox 和 owner 为边界，不提供我们要求的完整跨重启任务恢复。因此不能用它替换 Cloud 的持久任务记录、操作回执或恢复逻辑。

## 3. 小修复与依赖升级的实际范围

Anthropic 预算修复值得保留，但当前 `models_direct.rs` 的 Anthropic 默认装配没有开启 extended thinking，`assembly.rs` 的 GoalMiddleware 也没有配置辅助验证模型。它是相关能力启用后的防护，不是本次已证实的默认生产阻塞项。

Workspace MCP 修复的重要点是“已知未创建”与“创建结果未知”分开处理。只有前者能安全结算；不能把所有超时或取消统一当成未执行。并发上限调整属于配额策略，不能随补丁盲目复制。

上游依赖升级还涉及 ACP 类型、资源存储、fs2→fs4、sha2、YAML 等，并非只替换一个 rmcp 版本。应同步审查锁文件、补丁路径和校验值、文件锁及哈希调用、本项目允许的协议能力，不覆盖本项目 Cargo.lock 或照搬完整 workspace。

## 建议同步顺序

1. 保持当前候选版本，先迁入能够确认调用路径的小型修复，每项单独记录来源和针对性验证。
2. 单独推进归档投影与异步结果消费保护，适配 CloudJournal、账号授权、持久恢复和执行窗口；这些是下一轮最有价值的架构升级。
3. 再成组更新 MCP/ACP 与依赖闭包，重新应用生产补丁，并使用 rmcp 补丁构建脚本验证。

沿用仓库既定的叠加清单和生产补丁机制，不直接 merge/rebase 上游仓库。同步中继续保留原 Agent loop 与 PermissionMiddleware、executor 传输校验、设备和工作区固定目标、未知结果不重放、独立调度器、QQ MessageAdapter，以及用户创作的提示词。

本次没有修改运行代码或同步基线，以上建议不构成新增版本的上线验收。
