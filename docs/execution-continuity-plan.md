# 执行连续性重构

状态：实施中。范围以本线程完整 goal 为准；本文件记录阶段、契约和验证证据，不把设计标成完成。

## 阶段

1. 独立执行身份、可复用会话、任务与窗口账本；规范化工作区与隐私隔离；同会话串行受理。
2. 持久检查点、暂停/恢复/外部等待；安全换窗、交接与有界历史检索；未知副作用只查询。
3. 主助手独立审批回合、精确调用归属和删除前通知；与原权限中间件衔接。
4. 主助手按调用选择设备/工作区；授权发现、环境加载、共同资源互斥与操作回执。
5. 产物/证据/验收与版本化任务指令；任务事件、提示词和动态摘要。
6. 针对性回归、模拟模型与真实本地执行器联调、格式和 Clippy、可编辑拓扑与文档、提交推送。

## 不变量

- principal 来自认证；共享需显式选择且设备、规范化工作区及隐私范围一致。
- 逻辑执行会话可跨任务和窗口存在，窗口更换不能改变已受理操作的身份。
- 主助手继续摘要式压缩；执行窗口有界交接，trace 是证据，不是指令或个人长期记忆。
- 任务目标/指令、宿主事实、agent 工作理解与验收证据分别记录。
- 原 Agent loop 与 PermissionMiddleware 保持权限权威；运输认证独立。
- 所有自动审批保留精确身份和请求绑定；删除先通知再执行，不增加人工确认。
- 未知执行/投递不得重放；停机、暂停、取消和换窗不表示副作用已撤销。
- 本次不使用子 agent，不接生产部署，不添加付费依赖。

## 完成证据

逐项记录测试与联调证据，最终检查：复用、多任务隔离、低预算换窗、等待/审批/执行中重启、未知结果、跨设备固定归属、写入互斥、删除通知、最新指令/隐私/取消、产物与验收。未完成项不得宣称已交付。

## 实施记录

### 执行会话基础（2026-10-19，进行中）

- schema 17 独立保存逻辑执行会话、稳定 agent 身份和物理窗口映射；移除任务表的 worker_session 唯一约束，保留原任务/轮次及未知结果记录。
- delegate_task 接受可选 execution_session，list_execution_sessions 提供有界、授权过滤后的候选。未显式指定时新建，指定后核验 OAuth principal、设备、执行器规范化路径及文件系统身份、隐私范围和记忆隐私代次。
- 共享私聊上下文记录每个来源主会话的 context_generation；任一来源被清空/回退后拒绝复用及继续执行。公共会话按原受众隔离，不继承其他群的历史。
- 同窗口任务按持久 rowid 顺序派发；每个任务保留独立记录及工具归属。审批入口按实际 turn 查找任务父会话，不依赖 worker_session 唯一性。
- 尚未交付：实际窗口轮换、持久等待与恢复、主助手审批代理、多设备按调用执行、结构化产物验收和拓扑更新。这些仍属于同一个完整目标。

下一阶段：在原循环工具派发前和整批结果落账后写检查点，明确 model_boundary / dispatching / tools_settled；先证明恢复边界，再接暂停、换窗及旧回执核对。不能仅因执行器没有活跃任务就认定旧调用未执行。

本阶段验证：`test --locked -j 1 -p peri-cloud --lib --test gateway --test cloud_journal` 共 185 项通过（117 + 61 + 7）。新增 5 项状态/隔离/迁移回归与 1 项模拟模型、真实本地执行器联调，覆盖两个独立主会话复用同一执行上下文、各任务记录独立。`fmt -p peri-cloud -- --check`、`clippy --locked -j 1 -p peri-cloud --all-targets --no-deps -- -D warnings` 通过。均使用 rmcp 补丁包装脚本；不代表完整目标已验收。

### 持久检查点基础（实施中）

schema 18 增加独立的检查点和操作账本。原循环通过任务中间件在模型调用前保存 model_boundary，在实际派发前持久记录 dispatching 意图，在整批工具结果提交后保存 tools_settled 及回执。每份快照带原窗口/轮次、内容摘要和任务记录版本；同一调用 ID 更改参数或回执会冲突。

检查点不宣称执行器空闲，恢复前仍须认证查询原执行器。取消后已取得的工具结果允许落账，不能以取消请求抹掉实际结果。主助手可通过 inspect_task 的 operations 视图读取有界预览、参数指纹、实际窗口/轮次及结构化执行状态；未记录回执明确表示未知，不能重放。

本阶段尚未接入自动恢复、暂停唤醒及窗口替换。下一步是以操作账本查询原调用并补齐回执，证明恢复边界后再受理新的运行轮次。

恢复实施注意：当前账本保存模型 call_id；接下来必须从实际 ToolContext 持久保存原执行器 invocation_id 与绑定，不得假定两者相同或另造调用身份。云端工具应查询各自原幂等记录。只有核验快照与原操作后才能结算旧 RecoveryRequired 轮次并创建新的任务运行轮次；不能仅把 task.turn 清空再跑。新的运行轮次和窗口必须保留旧轮次索引。

检查点基础验证：上述 185 项定向测试再次通过。联调扩展为第二项任务实际 Write，经其真实执行会话审批后写入本地执行器，主助手通过 operations 读取已记录回执、原窗口/轮次和参数指纹。当前验证仍走既有人工 broker；主助手自动审批是后续阶段，不能用此记录声称已经完成。严格 Clippy 通过。

### 执行连续性（schema 19，实施中）

已接通：真实 ToolContext 的执行器调用身份持久化、原回执查询与单独的对账证据、任务运行轮次、协作暂停/恢复、外部等待、主助手回复唤醒，以及有界接班材料和物理窗口替换。主助手仍使用原摘要压缩；执行 agent 改用窗口轮换。旧窗口永久隔离于普通会话选择。工具契约见 [执行连续性](execution-continuity.md)。

新联调覆盖：低预算多次换窗并读取旧窗口的实际 Read 结果；等待及暂停跨重启保留并显式恢复；主助手问题等待跨重启后由消息唤醒；模拟“执行器已提交而云端未落账”的故障状态，对原回执返回 404 时不启动新推理、不再次 POST，回执恢复可查后查询续接且提交次数保持一次。故障状态为受控注入，不等于完成所有真实进程强杀时机的验收。

本阶段仍使用原人工审批链验证真实 Write，主助手审批代理尚未交付。跨设备按调用执行、结构化产物与验收、观察刷新策略、完整详情/筛选及拓扑更新继续实施；最终仍须执行完整目标的逐项验收和 GitHub 推送。

完整目标的未完成项集中记录于 [验收清单](execution-continuity-verification.md)。尤其是旧后台操作仍运行时的新窗口查询、真实强杀时机、自动审批和删除通知，不能用当前已结算操作的恢复联调替代。

schema 19 阶段检查：README 指定六个 crate 的测试全部通过（汇总见验证日志），变更 peri-cloud / peri-remote-tools 的严格 Clippy 和格式检查通过。新增执行连续性联调六项；原回执缺失与强杀状态使用受控注入。此阶段不含自动审批及最终目标完整交付。
