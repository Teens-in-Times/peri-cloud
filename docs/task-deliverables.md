# 任务产物与验收

执行结束、产物登记、验证证据和验收结论分别保存。`completed` 只表示执行循环已结束，不等于验收通过。第一版由原主助手验收，不创建验证 agent。

## 工具契约

执行 agent 使用 `record_artifact(task_id, expected_revision, operation, label)` 登记产物。operation 是本任务 operations 视图里的序号，必须关联成功且已结算的原生 Read、Write 或 Edit。路径、设备和规范工作区来自实际调用及宿主冻结绑定，模型不能另外指定位置。宿主保存原始回执版本；Write 额外保存提交内容的 SHA256。Read/Edit 的回执摘要不能冒充完整文件内容摘要。

执行 agent 使用 `record_verification(task_id, expected_revision, operation, label, artifacts)` 关联实际 Read、Bash、Grep 或 Glob 验证。passed 从结构化执行状态和退出码产生，不采信工具正文中的“成功”字样。标签说明检查覆盖什么，但这是 agent 的解释，主助手必须阅读实际证据判断覆盖范围。运行中、未知、失败和非零退出码不能作为通过证据。

主助手使用 `inspect_deliverables(task_id)` 读取有界产物、验证记录和验收历史。最多 16 个当前产物、32 条验证和 32 条验收；超出容量明确失败，不静默截断或覆盖关键证据。同一设备和工作区下重新观察同一路径会更新当前登记，旧操作回执保留。

主助手使用 `review_task(task_id, expected_revision, outcome, reason, verifications, unverified)` 保存 accepted/rejected。接受必须同时满足：

- 本轮执行已经完成。
- 选定验证均有实际成功回执，覆盖所有当前产物，且没有未验证项。
- 当前产物和验证匹配最新指令水位；所有补充要求已经明确标记应用。
- 产物观察后没有本任务的新写入或 Shell 操作；验证与后续产物观察之间也没有其他修改。
- 任务版本和指令版本在提交时仍一致。

accepted 是动态核验结果。旧验收记录不改写；新增要求、重新执行或证据版本变化会使其失效。宿主负责证据存在、归属、版本和执行事实；语义正确性仍由主助手结合当前目标、约束、验收要求及原始结果判断，不能只引用工作者结论。

## 后续要求与恢复

已完成任务允许 message_task 增加要求，立即使旧验收过期，但不会自动重跑。主助手显式 control_task(action=resume) 继续同一任务；目标独立的新工作使用 delegate_task。失败任务同样可显式恢复，取消或隐私失效任务不可借恢复绕过边界。

schema 21 在原操作账本保存受理时的指令水位，旧操作默认为未知版本，不能冒充针对新要求的验证。任务 JSON 内独立保存产物、验证和验收；重启保留原记录，恢复查询原操作，不再次登记或执行旧调用。历史与个人长期记忆分离。

证据是操作发生时的快照，不是持续文件监控。第一版保守地把全部 Shell 当成可能修改：若验证 Shell 在产物之后运行，需要在最终修改后重新读取产物。其他任务或外部程序之后改变文件，不会自动把旧任务的历史验收改成文件监控报告。需要当前状态时应重新执行授权读取和验证。

## 验证状态

模拟模型和真实本地执行器联调覆盖实际写入、读取、产物登记、拒绝无证据接受、带证据接受、新要求导致过期及重启保留历史。199 项定向回归、最终源码新增联调和严格检查通过，结果记录在实施计划；完整架构尚有跨设备按调用执行等工作，见验收清单。
