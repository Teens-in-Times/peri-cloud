# 个人预览运行与恢复

此页描述已有入口和部署前检查，不代表这些监控已在生产安装。

## 区分四种健康状态

| 层次 | 如何检查 | 不能推断什么 |
| --- | --- | --- |
| 进程 | HTTPS 门户、healthz、服务退出状态 | 不证明模型、QQ 或设备可用 |
| 渠道 | 已认证 QQ/OneBot 连接及实际收发 | 登录成功不代表客户端显示与主动发送已验收 |
| 模型 | 经明确授权的少量真实请求 | 配置可保存不代表协议、工具调用与上下文预算兼容 |
| 执行器 | 工作台连接检查，认证后的设备与版本 | 设备登记、租约或 TCP 连通不等于工具执行成功 |

建议部署侧监测服务反复重启、磁盘剩余空间、数据库和日志增长、长期等待及未知操作。先给出明确阈值与处理责任，再接入已有监控，不要求引入新的监控平台。

## 任务为什么没继续

先使用 QQ /状态、/结果 或网页现有会话状态；需要任务细节时，让主助手读取 list_tasks 和 inspect_task。不要通过重新下达相同任务判断旧任务是否成功。

| 状态 | 应核对的事实 | 继续方式 |
| --- | --- | --- |
| 等待主助手 | inspect_task 的 messages、approvals 与当前要求 | 由主助手回复或重新处理当前请求，不复用过期审批 |
| 等待设备 | 认证连接、固定设备和工作区 | 恢复原设备通路，再查询原操作；新设备不继承旧动作 |
| 等待容量 | 真实运行任务与未结算操作 | 保留账本，由原容量机制重新受理；不删除占用记录 |
| 运行或结果未知 | inspect_task(view="operations") | 查询原操作，必要时分页读原输入输出；无回执就保持未知 |
| 主助手直接操作未知 | inspect_device_operations | 查询原冻结目标与 invocation，不能重新提交代替查询 |
| 删除通知未知 | 原审批、发件状态及渠道恢复 | 不自动重发通知、不放行后续动作；恢复连通不等于原投递成功 |
| 用户修改要求 | 最新 instruction_version 与任务 revision | 更新后显式恢复；旧审批和旧验收不能代替当前决定 |

取消表示请求停止，暂停表示到安全边界停下；都不证明已经发生的副作用被撤销。产物与验证是当时的证据，外部修改后需重新观察。

## 备份与升级

数据库和备份包含账号凭据、模型 Key、私人历史，必须按凭据保护。使用 SQLite backup API 或部署环境的等价一致快照，不只复制 WAL 模式的主文件。备份运行配置、凭据、上下文目录时保持独立受限存储，禁止加入源码与 Release。

升级前记录旧二进制 BUILD.json、当前 schema、状态位置和备份。排空入口及任务后停止唯一宿主，保存最终快照，核对新包 SHA256SUMS。仅在未接收新业务的验证阶段，才能按预定流程恢复旧二进制与对应旧快照。开始接收新业务后应优先前向修复，不能直接回退到旧数据库丢弃新消息和原操作回执。

scripts/prepare-upgrade-baseline.py 与 scripts/smoke-upgrade.py 只用于新建的测试状态目录。它们不会备份或迁移生产；实际副本演练需要单独授权和受保护的运行环境。

## 本候选后的真实验收

使用受控测试工作区和无私人内容的任务：QQ 委派后继续聊天 → 补充要求 → 另一授权设备的小操作 → 执行窗口续接 → 暂停/继续 → 核验实际产物与回执 → 接收最终回复。再分别验证设备断线、宿主重启及主动联系窗口外静默。

当前不新增绕过未知结果的人工“强制成功”按钮，不以直接改库作为恢复步骤。真实平台缺少原消息查询能力时，保留这一限制并选择明确的新业务动作，而不是偷偷重放旧动作。
